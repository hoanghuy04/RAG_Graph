Bối cảnh

Sơ đồ hiện tại chia đôi quyền sở hữu hội thoại

Trong sơ đồ gốc, Chat Session Service ở Java (layer 2) giữ "Session · History metadata · AI Service Client" — một lớp vỏ mỏng. Cùng lúc đó, Conversation Service trong RAG Pipeline ở Python (layer 3) giữ "Multi-turn history · Redis cache", và Message Service cũng ở đó xử lý luôn cả streaming lẫn lưu trữ. Hai service ở hai ngôn ngữ, hai database, cùng tự nhận là nơi giữ lịch sử hội thoại — không rõ bên nào là nguồn sự thật khi cần đối chiếu.

Kiểm tra code thực tế: Main/backend-java mới chỉ có entity ChatModel (cấu hình LLM provider, không phải hội thoại); Main/backend-py mới chỉ có route /api/v1/chat/stream trả về mock response. Cả hai phía đều chưa build phần này — đây là quyết định greenfield, không có dữ liệu cũ cần di chuyển.

Đề xuất

Java sở hữu bảng conversations và messages trong PostgreSQL của layer 2 — ngang hàng với users, roles, documents mà nó đã quản lý. Mỗi lượt hỏi, Java gửi kèm lịch sử hội thoại trong request tới Python.

Python không lưu gì giữa hai request. Conversation Service hiện tại bị xoá vai trò lưu trữ; phần sinh câu trả lời (streaming SSE, citation, hallucination guard) đổi tên thành Response Service và chỉ hoạt động trong phạm vi một request.

Cân nhắc

Vì sao gộp, và cái giá phải trả

Ủng hộ gộp vào Java

  • Hội thoại gắn với user_id, org-scope, RBAC — dữ liệu này đã sống trong Postgres của Java, giữ cùng chỗ tránh JOIN xuyên database.
  • AuditLog Service đã có sẵn ở Java — ghi log truy cập hội thoại tái dùng được ngay, không phải xây lại ở Python.
  • Một nguồn sự thật duy nhất: không còn tình huống Java và Python "cãi nhau" về lịch sử hội thoại nào mới nhất.
  • Python có thể redeploy, scale, hoặc thay engine RAG mà không kéo theo rủi ro mất dữ liệu hội thoại.

Cái giá phải trả

  • Mất cache Redis nội bộ phía Python cho việc dựng ngữ cảnh nhanh — phải build lại (nếu cần) ở tầng Java.
  • Payload mỗi request tới Python lớn hơn vì phải kèm đủ lịch sử hội thoại thay vì chỉ session id.
  • Access Context Verifier vẫn cần Java ký HMAC — không đổi, nhưng giờ còn cần đảm bảo lịch sử gửi kèm khớp với quyền truy cập tài liệu của người dùng.

Mở rộng đề xuất · chốt bởi người ra quyết định

Chat vãng lai: PostgreSQL, user_id NULL, kèm IP

Người chưa đăng nhập không có user_id để gắn vào conversations/messages. Hai bản trước của mục này đề xuất tách guest chat ra Redis; quyết định cuối cùng đi theo hướng khác — giữ guest chat trong cùng bảng Postgres, chấp nhận không cần cơ chế dọn rác.

Bối cảnh — vì sao câu hỏi này xuất hiện

lisa có viết sẵn ChatCacheService (Redis/file, khoá theo session_id) nhưng nhánh gọi nó chỉ chạy khi db is None — mà endpoint thật luôn truyền db: SessionDep, không Optional. Guest chat của lisa vì vậy luôn đi thẳng vào Postgres với user_id = NULL, và bảng chats của lisa vốn đã có sẵn cột ip, user_agent, device_type cho mọi row — kể cả row không có chủ. Đây chính là điểm bản đính chính trước bỏ sót: guest chat của lisa không phải "vô danh hoàn toàn", nó đã có IP đi kèm.

Quyết định cuối

Đi theo Option A — chat vãng lai ghi thẳng vào conversations/messages của Java, cùng bảng với user đã đăng nhập, user_id = NULL. Không có TTL, không có job dọn rác — dữ liệu ở lại vĩnh viễn như hội thoại của user thật.

Bù lại phần "vô danh": mỗi row guest ghi kèm ip_address (và user_agent nếu cần) tại thời điểm tạo — đúng cách lisa đã làm cho toàn bộ bảng chats, không phải phát minh riêng cho Main. IP không thay thế được RBAC/audit của user thật, nhưng đủ để có một đầu mối truy vết nếu cần, mà không phải xây thêm hạ tầng cache hay luồng "claim" khi đăng nhập giữa chừng — chỉ cần một câu UPDATE gán user_id vào row đã có sẵn.

Checklist triển khai

  • Thiết kế bảng conversations / messages trong Postgres của Java (tối thiểu: id, user_id nullable, ip_address, department scope, created_at; message: role, content, citations, created_at).
  • Xoá entity/service stub ChatSessionService khỏi Main/backend-java (hiện chưa có code — chỉ cần gỡ khỏi kế hoạch/sơ đồ).
  • Thêm conversation_id + history[] vào contract của POST /ai/chat/query.
  • Đổi tên Conversation Service phía Python thành Response Service — không đọc/ghi gì giữa hai request, kể cả cho guest.
  • Cập nhật sơ đồ System Architecture: bỏ hẳn ô "Conv history cache ?" khỏi Redis, cập nhật nhãn mũi tên Layer 2 → Layer 3.
  • Ghi ip_address (từ request gốc, qua API Gateway) vào mỗi conversation khi tạo — áp dụng cho cả guest lẫn user thật.
  • Giới hạn tập tài liệu công khai mà chat vãng lai được phép truy vấn — enforce ở Java trước khi gọi Python, không dựa vào Python tự lọc.
  • Khi guest đăng nhập giữa chừng: UPDATE conversations SET user_id = ... WHERE id = ... trên row hiện có.
